# TaskManager API 使用指南

面向外部系统对接：数据集创建 → 任务创建（含复制样板）→ 进度查询与重试 → judge 明细拉取。

- Base URL：`http://<host>:8888/api/v1/task`
- 统一响应包络：

```json
{"status_code": 0, "status_msg": "ok", "data": { ... }}
```

`status_code != 0` 表示失败，`error_code` 给机器可读原因（`BAD_REQUEST` / `FORBIDDEN` / `NOT_FOUND` / `INTERNAL_ERROR` 等）。

---

## 0. 鉴权

绝大多数接口**公开**。仅以下 **8 个**需要权限：

| 接口 | 说明 |
| --- | --- |
| `GET /testsets/{id}` | 测试集详情 |
| `GET /testsets/{id}/cases` | 测试集 cases |
| `POST /tasks/{id}/start` | 启动任务 |
| `POST /tasks/{id}/pause` | 暂停 |
| `POST /tasks/{id}/cancel` | 取消 |
| `POST /tasks/{id}/reset_failed` | 重试失败 |
| `POST /tasks/{id}/fill_missing` | 补齐缺失 |
| `POST /engine/*` | 调度引擎控制 |

**注意**：`POST /tasks`（创建任务）、`PUT /tasks/{id}`（改任务）、
`POST /tasks/{id}/retry-recall`（补抓）、`generate_judge`、`judge 下载`
以及所有查询接口均为**公开**。

鉴权通过请求头或 cookie 传当前用户（由网关 SSO 或调用方注入）：

| 方式 | 字段 | 示例 |
| --- | --- | --- |
| Header（推荐） | `X-User-Id` / `X-User-Name` | `X-User-Id: huangdaqiang` |
| Cookie | `user_id` / `user_name` | `user_id=huangdaqiang` |

用户需在 `[task_manager] allowed_users` 白名单内，否则返回 `403 FORBIDDEN`。

## 1. 创建数据集

### `POST /testsets`

JSON 直接传 case 列表。

```bash
curl -X POST 'http://<host>:8888/api/v1/task/testsets' \
  -H 'Content-Type: application/json' \
  -d '{
    "name": "我的测试集",
    "description": "可选描述",
    "cases": [
      {"case_id": "c1", "input_list": [{"query": "贵州茅台现价"}]},
      {"case_id": "c2", "input_list": [{"query": "宁德时代市值"}]}
    ]
  }'
```

响应：

```json
{"status_code": 0, "data": {"testset_id": "36c4c1a2273347ae", "total_count": 2, ...}}
```

**case 结构**：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `case_id` | 否 | 不传自动生成 `<prefix>_<序号>` |
| `input_list` | 是 | `[{"query": "问句"}]`；多轮就放多条（每轮一个 query）|
| `query` | 替代 | 若不传 `input_list`，可用 `query` 单条，会自动转成 `input_list` |
| 其它 | 否 | `rubric` / `tags` 等原样保留，供 judge 使用 |

### 多模态（图片输入）

**多模态走 `input_list[]` 里的图片字段**，有两种互斥写法：

#### 写法 A：`image_base64`（推荐，无需外网可达）

```json
{
  "case_id": "c1",
  "input_list": [{
    "query": "这张图里是什么股票？",
    "image_base64": "iVBORw0KGgoAAAANSUhEUg...",
    "file_name": "kline.png",
    "content_type": "image/png"
  }]
}
```

服务端会自动：
1. `base64` 解码 → 存入 **GridFS**
2. 把 `image_base64` 换成 `image_ref: {file_id, file_name, mime}`
3. 执行时从 GridFS 读二进制直接上传，**不依赖外网 URL**

> 为什么要转换：base64 直接存进 `cases` 会撞 **MongoDB 16MB 单文档上限**。
> 转换在 `create_testset` / `append` 两处都会做（`_process_images_to_gridfs`）。

#### 写法 B：`public_url`（已有可访问的图片链接）

```json
{
  "case_id": "c2",
  "input_list": [{
    "query": "这张图里是什么？",
    "public_url": "https://oss.example.com/img/xxx.png"
  }]
}
```

执行时直接按 URL 下载再上传。**要求该 URL 在服务端容器内可达**（内网 OSS 可以，公网受限时请用写法 A）。

#### 支持的 fetcher（重要差异）

| fetcher | 支持情况 |
| --- | --- |
| **`new`** | ✅ 完整支持：`image_base64`（→GridFS）或 `public_url` |
| **`realtime`** | ⚠️ **只支持 `public_url` + `download_url` 两个字段同时给**，且**不支持** GridFS 的 `image_ref`（即 `image_base64` 转存后无法用）|
| `lumi` / `workbuddy` | ❌ 当前**不消费**图片输入（沙盒链路未接多模态）|

**结论**：
- 走 `new`（新架构）的多模态任务：用 `image_base64` 最省心
- 走 `realtime`（老架构）：必须在 case 里同时提供 `public_url` 和 `download_url`，且两者都需服务端可达
- 走 `lumi` / `workbuddy`：暂不支持图片，只能纯文本

#### 关于 case 级的 `media_url_list`

case 根上可以带 `media_url_list` / `media_info_list`，但它们**只是原样透传的元数据**
（供外部溯源/judge 展示），**不会被执行期当作图片输入**。
要真正发送图片，必须放在 `input_list[]` 上（字段见上表）。

**大规模数据**：接口单次建议 ≤ 100 条，更多请分批：

```bash
# 先建（第一批）
POST /testsets            {"name": "...", "cases": [前 100 条]}

# 再追加（每次 ≤ 100 条）
POST /testsets/{testset_id}/append   {"cases": [下一批]}
```

`append` 是原子 `$push`，支持并发追加，按 `case_id` 去重。

**Excel 上传**：如数据在表格里，用 `POST /testsets/upload`（`multipart/form-data`，字段 `name` / `file` / `description`）。

## 2. 创建任务（复制样板任务）

后端**没有** `copy_task` 接口。复制样板的标准做法是：
**读样板 → 改关键字段 → 创建新任务**。

### 步骤 1：读取样板任务的完整配置

```bash
curl 'http://<host>:8888/api/v1/task/tasks/<样板task_id>'
```

返回里这些字段可以直接复用到新任务：

| 字段 | 用途 |
| --- | --- |
| `pipeline` | **step 配置全在里面**（见下）|
| `concurrency_limit` | 并发上限 |
| `concurrency_schedule` | 按小时节奏（可选）|
| `testset_selections` | 测试集及 limit/seed |

`pipeline.steps[]` 每项结构：

```json
{
  "key": "lumi-test",
  "fetcher": "lumi",
  "is_pre": false,
  "is_deep": false,
  "mode": "expert",
  "user_id": "",
  "schedule_user_id": "",
  "agent_id": null,
  "history": false,
  "event_name": null,
  "ab_test_content": null,
  "litefuse_recall": "off",
  "lumi_profile_id": "lp_3d78cc20626144cc"
}
```

`fetcher` 取值：`realtime`（老架构）/ `new`（新架构）/ `agent`（旧测评）/
`lumi`（Lumi 客户端经沙盒）/ `workbuddy`（WorkBuddy RPA 经沙盒）。

> **注意**：`lumi` / `workbuddy` 的 step **必须**带 `lumi_profile_id`（沙盒预设），
> 且同一任务内不同 step 可以用不同预设。预设 id 可从
> `GET /lumi/profiles/{app_type}` 获取。

### 步骤 2：创建新任务

### `POST /tasks`

```bash
curl -X POST 'http://<host>:8888/api/v1/task/tasks' \
  -H 'Content-Type: application/json' \
  -H 'X-User-Id: yourname' \
  -d '{
    "task_name": "新任务名",
    "description": "可选",
    "testset_selections": [
      {"testset_id": "36c4c1a2273347ae", "limit": 5}
    ],
    "concurrency_limit": 2,
    "pipeline": {
      "is_cn": true,
      "parallel": true,
      "with_pic": false,
      "add_history": false,
      "steps": [
        {"key": "A-expert", "fetcher": "new", "is_deep": true, "mode": "expert"},
        {"key": "lumi-test", "fetcher": "lumi", "lumi_profile_id": "lp_3d78cc20626144cc"}
      ]
    }
  }'
```

响应：`{"data": {"task_id": "7cfb2bbf422d4e9b", "total_count": 10, ...}}`

**关键字段说明**：

| 字段 | 说明 |
| --- | --- |
| `testset_selections` | **推荐**。每项可独立 `limit` / `random_seed`，多个测试集合并时总数为各自 limit 之和 |
| `testset_id` / `testset_ids` | 简化写法（单/多测试集），与 `testset_selections` 三选一，后者优先 |
| `limit` / `random_seed` | 顶层简化写法。`random_seed>0` 随机抽 N 条，否则按顺序取前 N 条 |
| `pipeline.parallel` | `true` 时各 step 并发执行 |
| `concurrency_limit` | 任务级并发（同时跑几个 case）|

### 步骤 3：启动

创建后任务为 `created` 状态，需手动启动：

```bash
curl -X POST 'http://<host>:8888/api/v1/task/tasks/<task_id>/start' \
  -H 'X-User-Id: yourname'
```

## 3. 查询进度、重试、补缺

### 3.1 查询进度

### `GET /tasks/{task_id}`

```bash
curl 'http://<host>:8888/api/v1/task/tasks/<task_id>'
```

进度相关字段：

| 字段 | 含义 |
| --- | --- |
| `status` | `created` / `running` / `paused` / `completed` / `cancelled` / `failed` |
| `total_count` | **总量** |
| `completed_count` | **全部 step 成功** |
| `partial_count` | **部分 step 成功**（有缺失）|
| `failed_count` | **全部 step 失败** |
| `active_count` | 正在执行中的 item 数（派生自 items，实时准确）|

判读：

```
已完成 = completed_count + partial_count + failed_count
未开始/进行中 = total_count - 已完成
```

**「缺失」的定义**：一个 item 内**并非所有 step 都成功**即计入 `partial_count`（部分成功）
或 `failed_count`（全失败）。要看**具体缺哪个 step**，查 item 明细：

```bash
curl 'http://<host>:8888/api/v1/task/tasks/<task_id>/items?status=partial&page=1&size=50'
```

每条 item 含：

```json
{
  "item_id": "..._000001",
  "status": "partial",
  "success_keys": ["A-expert"],          // 成功的 step
  "missing_keys": ["lumi-test"],         // 缺失的 step ← 直接看这个
  "error": "missing keys: ['lumi-test']",
  "retry_count": 0
}
```

参数：`status` 按状态过滤（`completed` / `partial` / `failed` / `pending` / `running`），
`page` 从 1 起，`size` 最大 200。

单条详情：`GET /tasks/{task_id}/items/{item_id}`（含完整 `result` 与 `judge_data`）。

### 3.2 重试失败（整条重跑）

### `POST /tasks/{task_id}/reset_failed`

把 `failed` 的 item 重置为 `pending`，**整条 item 的所有 step 全部重跑**。

```bash
curl -X POST 'http://<host>:8888/api/v1/task/tasks/<task_id>/reset_failed' \
  -H 'X-User-Id: yourname'
# → {"data": {"task_id": "...", "reset_count": 3}}

curl -X POST 'http://<host>:8888/api/v1/task/tasks/<task_id>/start' \
  -H 'X-User-Id: yourname'
```

> 只重置 `failed`，不动 `partial`。且会清空 `fill_keys`（确保全量重跑）。

### 3.3 补齐缺失（只补缺失的 step）

### `POST /tasks/{task_id}/fill_missing`

把 `partial` 的 item 重置为 `pending`，**只重跑 `missing_keys` 里的 step**，
已成功的 step 结果保留不重跑。这是**优先使用**的恢复方式（省时间省额度）。

```bash
curl -X POST 'http://<host>:8888/api/v1/task/tasks/<task_id>/fill_missing' \
  -H 'X-User-Id: yourname'
# → {"data": {"task_id": "...", "fill_count": 5}}

curl -X POST 'http://<host>:8888/api/v1/task/tasks/<task_id>/start' \
  -H 'X-User-Id: yourname'
```

**已完成的任务也可以补齐**：若任务已 `completed` 但仍有 `partial` item，
补齐后任务状态会回退为 `created`，重新 `start` 即可。

### 3.4 补抓日志（日志未就绪导致的缺失）

### `POST /tasks/{task_id}/retry-recall`

大批量任务时日志服务写入延迟高，step 会因「日志回溯为空」被判失败。
这些 step 的 `result` 里带着 `trace_id`，日志就绪后**无需重跑推理**，补抓即可恢复。

```bash
curl -X POST 'http://<host>:8888/api/v1/task/tasks/<task_id>/retry-recall?max_wait_sec=180' \
  -H 'X-User-Id: yourname'
```

响应：

```json
{"data": {"scanned": 3, "items_fixed": 3, "steps_fixed": 6,
          "details": [{"item_id": "...", "recovered": ["A-expert","lumi-test"],
                       "new_status": "completed"}]}}
```

参数 `max_wait_sec`（默认读配置 180s）：单条 trace 的日志等待预算。

**适用判断**：item 的 `error` 或 step 的 `error` 里出现
`reason=not_ready` / `no_node` / `network_error` 时适合补抓；
业务失败（`QUESTION_FAILED` 等）补抓无效。

### 三种恢复方式怎么选

| 场景 | 用哪个 |
| --- | --- |
| 全部 step 失败（`failed`） | `reset_failed` 整条重跑 |
| 部分 step 成功（`partial`） | **`fill_missing`** 只补缺失（首选）|
| 日志未就绪类缺失 | **`retry-recall`** 连推理都不用重跑 |

## 4. 查询任务信息与 judge 明细

### 4.1 查任务配置（有哪些 step、具体配置）

### `GET /tasks/{task_id}`

完整返回 `pipeline.steps[]`（字段见第 2 节）。这就是「任务有哪些 step、
每个 step 用什么 fetcher / 什么预设」的唯一来源。

```bash
curl 'http://<host>:8888/api/v1/task/tasks/<task_id>' \
  | jq '.data.pipeline.steps[] | {key, fetcher, mode, lumi_profile_id}'
```

### 4.2 查会话索引（session_id / trace_id）

### `GET /tasks/{task_id}/cases`

轻量接口：返回每个 case 在每个 step 上的 `session_id` / `trace_id` / `ts`，
不读 `judge_data` 的大字段，用来批量取 trace 做外部溯源。

```bash
curl 'http://<host>:8888/api/v1/task/tasks/<task_id>/cases?page=1&size=100'
```

### 4.3 查 judge 明细（分页）

### `GET /tasks/{task_id}/judge/{key}/download`

按 **step key** 拉取该 step 的 judge 数据，JSONL 格式（每行一条）。

```bash
# ① 全量流式下载（gzip）
curl -o judge.jsonl.gz \
  'http://<host>:8888/api/v1/task/tasks/<task_id>/judge/A-expert/download'

# ② 分页拉取（推荐：先看总量，再逐页取）
curl 'http://<host>:8888/api/v1/task/tasks/<task_id>/judge/A-expert/download?page=1&size=100'

# ③ 带过滤
curl 'http://<host>:8888/api/v1/task/tasks/<task_id>/judge/A-expert/download?page=1&size=100&query=<case_id或问句片段>'

# ④ 按测试集过滤（多测试集任务时）
curl '...&testset_id=36c4c1a2273347ae'
```

**参数**：

| 参数 | 说明 |
| --- | --- |
| `key` | **路径参数**，step 的 key（从 `GET /tasks/{id}` 的 `pipeline.steps[].key` 取）|
| `page` | `0` = 全量流式下载（默认）；`≥1` = 分页模式，需配合 `size` |
| `size` | 每页条数，`page≥1` 时生效，最大 1000 |
| `query` | 按 `case_id` / 输入问句模糊过滤 |
| `testset_id` | 只取该测试集的 judge |

**响应**是 `application/gzip` 的 JSONL 流（不是标准包络），每行一个 judge 对象：

```json
{"case_id": "...", "trace_id": "...", "input": {...}, "answer": {...},
 "chain": [...], "meta": {"session_id": "...", ...}}
```

**分页拉取**：响应头带 `X-Total-Count`，先读它拿总数，再循环翻页：

```bash
# 第 1 页：先看响应头拿总数
resp_headers=$(curl -s -D - -o page1.jsonl.gz \
  "$H/tasks/$TASK/judge/A-expert/download?page=1&size=100" | grep -i x-total-count)
echo "$resp_headers"   # → x-total-count: 200

# 之后按 total/size 向上取整，循环拉 page=2..N
for p in $(seq 2 $(( (200 + 99) / 100 ))); do
  curl -s -o "page$p.jsonl.gz" \
    "$H/tasks/$TASK/judge/A-expert/download?page=$p&size=100"
done
```

> `page=0`（默认）是全量流式下载，此时也带 `X-Total-Count`。
> 若 `total <= 0` 会直接返回空体。

### 4.4 立即重造 judge

### `POST /tasks/{task_id}/generate_judge`

对任务内所有 `completed` / `partial` 且仍有 `result` 的 item 重新构造 `judge_data`
（写回 `item.judge_data`）。用于 judge 缺失/过期的修复。

```bash
curl -X POST 'http://<host>:8888/api/v1/task/tasks/<task_id>/generate_judge'
# → {"data": {"generated_items": 120, "key_counts": {"A-expert": 120}}}
```

> 若此前执行过「删除 logs」，`result` 已清空的 item 无法重造（无原始数据）。

## 附：完整对接流程示例

```bash
H='http://<host>:8888/api/v1/task'
U='X-User-Id: yourname'

# 1. 建数据集
TS=$(curl -s -X POST "$H/testsets" -H 'Content-Type: application/json' \
  -d '{"name":"demo","cases":[{"case_id":"c1","input_list":[{"query":"茅台现价"}]}]}' \
  | jq -r '.data.testset_id')

# 2. 读样板任务，取 pipeline
PIPE=$(curl -s "$H/tasks/<样板task_id>" | jq '.data.pipeline')

# 3. 用样板 pipeline 创建新任务
TASK=$(curl -s -X POST "$H/tasks" -H 'Content-Type: application/json' -H "$U" \
  -d "{\"task_name\":\"demo-run\",\"testset_selections\":[{\"testset_id\":\"$TS\"}],
       \"concurrency_limit\":2,\"pipeline\":$PIPE}" | jq -r '.data.task_id')

# 4. 启动
curl -s -X POST "$H/tasks/$TASK/start" -H "$U"

# 5. 轮询进度
while true; do
  D=$(curl -s "$H/tasks/$TASK")
  echo "$D" | jq -c '.data | {status, total_count, completed_count, partial_count, failed_count}'
  [ "$(echo "$D" | jq -r '.data.status')" = "completed" ] && break
  sleep 30
done

# 6. 有缺失就补齐（只补缺失 step）
curl -s -X POST "$H/tasks/$TASK/fill_missing" -H "$U"
curl -s -X POST "$H/tasks/$TASK/start" -H "$U"

# 7. 拉 judge 明细（按 step key）
curl -o "judge-A-expert.jsonl.gz" "$H/tasks/$TASK/judge/A-expert/download"
```

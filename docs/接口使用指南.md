## 两个接口，一查一看

| 接口 | 容器端口 | 干什么 |
|---|---|---|
| **5003 供数接口** | `5003` | 查数据：按条件筛 trace、看问题条目、数 P0–P4、按维度聚合 |
| **5002 页面接口** | `5002` | 看内容：把一条 trace 打开成对话详情页，并用 `trace` 参数直接定位到会话里的那一轮 |

```text
5003  $API/traces ...                      →  拿到 trace_id、session_id
        │  拼 case = split|model|session_id
        ▼
5002  $PAGE/?product=aime&case=…&trace=<trace_id>  →  打开该 trace 所在的那一轮
```

两个服务都只读、无鉴权、内部使用；数据每 10 分钟增量更新。

## 一、5003 供数接口

### 地址与通用约定

| 部署 | 对外地址 | 集群内地址 |
|---|---|---|
| 弗吉尼亚（AIME） | `http://10.217.219.2:2224/api/v1/analysis` | `http://interactive-npasm9ch66eb:5003/api/v1/analysis` |
| 乌兰察布（问财） | `http://117.50.195.94:3335/api/v1/analysis` | `http://interactive-i6piqwvlnsr5:5003/api/v1/analysis` |

- `GET` / `POST` 同语义（`/traces/batch` 只收 POST）；多值参数 GET 用逗号、POST 用数组。
- 所有 200 响应：`{request_id, schema_version: "2.0", data, meta}`；`meta.filters` 回显生效条件。
- `dataset` 必填，取值跟部署的数据集绑定：AIME 环境是 `aime_eval`；**问财环境的取值以该套部署为准**
  （5003 当前实现只接了 AIME，本文示例均以 AIME 为例）。
- 未知编码 / 未知严重度返回 422；`user_ids` 超 5000、`trace_ids` 超 1000 返回 413。
- `cursor` 翻页，30 分钟过期返回 410。

### 三个核心概念

1. **trace**：一条单轮对话，`trace_id` 来自 `turns[].meta.trace_id`。
2. **problem（问题条目）**：归因结果里真正的东西，带 `label`、`severity`(P0–P4)、`component`、`evidence`。
   一条 trace 可以有多个问题。**没有 `is_error`/`is_correct` 这种对错判定**（`is_correct` 恒 `null`，因为数据里没有标准答案）。
3. **problem code**：聚类流水线给问题映射的 `S9.M5.1` 这类编码。只有被聚类的问题才有，
   未聚类的 `code=null`——但它**仍然计入**问题数和 P0–P4 统计。

### 1. 数 P0–P4（最常用）

```bash
curl -s "$API/severity?dataset=aime_eval"
```

```json
{"data": {
  "total": {
    "analyzed": 21459, "traces": 21459, "problems": 57885,
    "severity": {
      "P0": {"problems": 370,  "traces": 353},
      "P1": {"problems": 4051, "traces": 3382},
      "P2": {"problems": 13689,"traces": 10041},
      "P3": {"problems": 7578, "traces": 6353},
      "P4": {"problems": 32197,"traces": 15434}
    },
    "unlabeled": 0
  },
  "groups": [], "next_cursor": null, "has_more": false
}}
```

- `severity.Pn.problems`：**有多少个 Pn**（问题条目数）。
- `severity.Pn.traces`：多少条 trace 至少有一个该等级的问题。
- `problems` = 所有等级条目之和 + `unlabeled`；各等级 `problems` 之和恒等于 `problems`。
- 筛选条件和其它接口一样（`source`、日期、`intent`、`problem`、`severity`、`app_version`、`user_ids`）。
- 可选 `group_by`（0–2 个维度，省略时只返回 `total`），例如：

```bash
# 按模型看 P0–P4
curl -s "$API/severity?dataset=aime_eval&group_by=app_version"
# 按天趋势
curl -s "$API/severity?dataset=aime_eval&group_by=day"
# 只看 P0/P1 的分布
curl -s "$API/severity?dataset=aime_eval&severity=P0,P1&group_by=source"
```

`group_by` 的 `groups[]` 每行与 `total` 同结构（`analyzed/traces/problems/severity/unlabeled`）。

### 2. 按维度聚合

```bash
# 问题（环节）分布：每个环节多少 trace、多少问题条目
curl -s "$API/summary?dataset=aime_eval&group_by=problem&level=top"
```

```json
{"data": {
  "total": {"analyzed": 21459, "traces": 21459, "users": 6309, "problem_traces": 19215, "problems": 57885},
  "groups": [
    {"keys": {"problem": "S9"}, "analyzed": 21459, "traces": 11181, "users": 3926,
     "problem_traces": 11181, "problems": 16677}
  ]
}}
```

- `group_by`：`intent`、`problem`、`day`、`user`、`app_version`、`source`（1–2 个）。
- `level`：`top`（环节）/`leaf`（最细编码）/`children`（筛选值的下一层），只作用于 `intent`、`problem`。
- `problem_traces`：至少一个问题条目的 trace 数；`problems`：问题条目数。
- `analyzed` 是分母：去掉 `problem`/`severity` 筛选、忽略 `problem` 分组维度后的 trace 数。
- 按 `problem` 分组时，每个问题条目只归一组，所以各组 `problems` 之和 = `total.problems`；
  `traces` 会跨组重复计；未聚类问题进 `{"problem": null}` 组。

### 3. 列 trace（最常用）

```bash
# 有 P0 的 trace
curl -s "$API/traces?dataset=aime_eval&severity=P0&page_size=2"
```

```json
{"data": {"items": [{
  "trace_id": "20003020179362744779700000000511", "day": "2026-11-02",
  "asked_at": "2026-11-02T…Z", "source": "prelaunch", "user_id": "…",
  "session_id": "thread_c043e0f324d9410491296a257cacfb2b",
  "app_version": "AIME-Atlas_expert", "query_preview": "…", "intent_code": "T06.S03",
  "is_correct": null, "problem_count": 2, "problem_codes": ["S9.M5.1"],
  "problems": [
    {"code": null,      "label": "在缺当日行情时虚构价格形态", "severity": "P2", "component": "answer_synthesis", "session_level": false},
    {"code": "S9.M5.1", "label": "旧数据当当前值",             "severity": "P2", "component": "answer_synthesis", "session_level": false}
  ],
  "analysis_id": "an_…", "analyzed_at": "2026-11-04T…Z"
}], "total": 353, "page_size": 2, "next_cursor": "…", "has_more": true}}
```

- 常用筛选：`source`、`start_day`/`end_day`、`intent`、`problem`、`severity`、`app_version`、`user_ids`、`q`。
- `problems` 是精简数组（`code/label/severity/component/session_level`）；完整定义与证据去详情接口。
- `ids_only=true` 只返回 trace_id（每页上限 5000），用于导出；**trace_id 不唯一**（跨模型/重跑会重复），按需去重。
- `total` 恒等于同条件下 `/summary` 的 `traces`。

### 4. 批量、单条、分类树

```bash
# 按一批 trace_id 取摘要（≤1000，返回顺序同请求）
curl -s -X POST "$API/traces/batch" \
  -H 'Content-Type: application/json' \
  -d '{"dataset":"aime_eval","trace_ids":["…","…"]}'

# 单条详情：eval_input 整行 + trace 对象 + 完整问题条目 + 历史版本（day 必填）
curl -s "$API/traces/<trace_id>?dataset=aime_eval&day=2026-11-02"

# 分类树：intent / problem / severity
curl -s "$API/taxonomy?kind=problem&app_version=AIME-Atlas_expert"
curl -s "$API/taxonomy?kind=severity"
```

- `batch` 按 `trace_id` 返回，同 id 的多个版本会合并成一条；未分析/未知 id 标 `status:"not_analyzed"`，字段为空。
- 详情里 `analysis.problems[]` 是完整条目（`code/label/severity/definition/reason/component/evidence/session_level`），
  `analysis.history[]` 是同一 trace 更早的分析版本。
- 跨轮（session 级）问题只挂在会话**最后一轮**，`session_level: true`；计数只算一次，不会在每轮重复出现。

### 注意点

- **P4 也计入**问题数；要不要把它当“提示级”，由消费方按 `severity` 自己判断。
- **未聚类问题**（`code=null`）照样计入 `problems` 与 P0–P4；只是不会出现在 `problem_codes` / 编码分组里。
- `problem_codes` 是已聚类编码去重结果；`problem_count` 等于 `problems` 长度。
- 时间统一 UTC，`day` 按 Asia/Shanghai 划分；数据延迟 ≈ 落盘 + 最多 10 分钟。

## 二、5002 页面接口

### 地址与链接格式

| 部署 | 对外地址 | 备注 |
|---|---|---|
| 弗吉尼亚（AIME） | `http://10.217.219.2:2222/` | 集群内 `http://interactive-npasm9ch66eb:5002/` |
| 乌兰察布（问财） | `http://117.50.195.94:2833/` | 集群内 `http://interactive-i6piqwvlnsr5:5002/` |
| DSW 代理（当前指向乌兰） | `https://rtahz.10jqka.com.cn/bmtp/proxy/dsw/trace-detail/` | 平台会剥掉路径前缀，前端用相对路径 |

下文示例统一用 `$PAGE` 表示目标环境的页面地址。

```text
/?product=aime&case=<split>|<model>|<session_id>&trace=<trace_id>
```

| 参数 | 说明 |
|---|---|
| `product` | `aime` / `wencai` |
| `case` | `split|model|session_id`（如 `daily|aime_expert|thread_…`），URL 里 `|` 写成 `%7C` |
| `slug` | 也可以传 10 位 slug；定位到一条评测输出，效果同 case |
| `trace` | 可选；5003 的 `trace_id`，打开后直接选中并滚动到该轮 |

### 从 5003 拼链接

| 页面参数 | 从 5003 取值 |
|---|---|
| `product` | 目标环境的产品：AIME 环境用 `aime`，问财环境用 `wencai` |
| `case` | `split` + `model` + `session_id`。AIME：`source=prelaunch`→`daily`、`feedback`→`lost`，`app_version` 以 `_expert` 结尾→`aime_expert`、`_fast` 结尾→`aime_fast`；问财同理用该环境召回索引里的 `sp`/`m` |
| `trace` | item 的 `trace_id` |

### 行为

- 命中 `trace`：选中该轮（`#ttabs` 高亮）、滚动到该轮，归因区显示该轮的问题；URL 保留 `trace`，刷新仍定位同一轮。
- 找不到：页面明确报错“没有找到这条 trace”，**不会静默停在其它轮**。
- 不带 `trace`：行为不变，多轮会话默认停在最后一轮。
- 手动点其它轮：自动从 URL 去掉 `trace`，避免地址栏与实际内容不一致。
- `trace` 必须和 `case` / `slug` 一起用；单独给 `trace` 无法定位到会话。

### 给程序用的 JSON 接口

| 接口 | 用途 |
|---|---|
| `GET /api/context?product=&case=&trace=` | 会话的召回索引行 + taxonomy；`trace` 原样回显（定位在前端/详情里做） |
| `GET /samples/<slug>.json` | 单条详情；`attribution.turns[].trace_id` 就是每轮 trace_id，可用它自己匹配轮次 |
| `GET /samples-<product>.json` | 全量召回索引（wencai ≈2 MB、aime ≈9 MB，建议 gzip） |
| `GET /healthz` | 存活 + 上游看板探活 |

## 五、FAQ

**Q：为什么没有 `is_error`？**
A：数据里没有标准答案，无法判定对错；`is_correct` 也是 `null`。有的只是分析出来的问题条目和严重度。

**Q：想要“错误率”怎么办？**
A：用 `/severity` 的 `severity.Pn.traces / total.analyzed`，自己定义哪几级算错误（比如只算 P0–P1）。

**Q：未聚类的问题会影响统计吗？**
A：计入 `problems` 和 P0–P4；只是没有 code，按编码分组时进 `null` 组。

**Q：为什么 `trace_id` 不能当唯一键？**
A：它只在 `(day)` 内基本唯一，跨模型/重跑会重复；详情必须带 `day`，导出需要去重。

**Q：页面提示“没有找到这条 trace”？**
A：trace 不在该 `case` 的会话里，或 5003 与看板数据快照有时间差（看板详情按需生成、索引缓存 120s）。
确认 `case` 的 split/model/session 拼对了，或去掉 `trace` 只看会话。

**Q：我该连乌兰还是弗吉尼亚？**
A：按数据：问财 → 乌兰察布（`117.50.195.94`，5003=`3335`、5002=`2833`）；
AIME → 弗吉尼亚（`10.217.219.2`，5003=`2224`、5002=`2222`）。当前 AIME 还在乌兰，
弗吉尼亚部署完成后切换；集群内调用优先用容器名 + 容器端口。

**Q：数据多久更新一次？**
A：5003 每 10 分钟增量重建；5002 的索引缓存 120 秒，详情实时向看板取。

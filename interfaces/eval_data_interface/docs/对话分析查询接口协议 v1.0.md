# 对话分析查询接口协议 v1.0

Nov 2, 2026 · @Jiang Wu

## 1. 概述

本协议定义 RSI 看板向对话分析组查询意图分类、问题分类和错误占比所用的 5 个只读接口。状态：待实现。分析组按本协议提供接口，看板按本协议接入。

| 接口 | 用途 |
| --- | --- |
| `GET /taxonomy` | 拉意图、问题分类树 |
| `GET\|POST /summary` | 按任意筛选条件聚合，按一到两个维度分组 |
| `GET\|POST /traces` | 按同一套筛选条件查 trace 列表 |
| `POST /traces/batch` | 按一批 trace\_id 取摘要 |
| `GET /traces/{trace_id}` | 取单条 trace 的完整内容和分析结果 |

### 1.1 分工

- 对话分析组：维护分类体系，对 trace 做意图和问题分析，并在分析结果上提供聚合与查询。
- 业务侧（不在本协议内）：用户信息、全量对话、业务计数、召回。
- `user_id` 在本协议中只是 trace 上的附加信息，标明对话由谁发起，用于按用户筛选；分析组不维护用户资料。看板从业务侧拿到用户组（一批 user\_id）后，传给本协议的接口做筛选。

### 1.2 地址与认证

- 接口前缀：`/api/v1/analysis`。服务根地址由分析组提供。
- 认证方式由分析组决定，建议沿用轨迹接口的 HTTP Basic + HTTPS。凭据由看板服务端携带，不进入浏览器。
- 请求头 `Accept: application/json`；POST 请求另带 `Content-Type: application/json`。

### 1.3 通用约定

- 所有接口只读。`/summary`、`/traces` 同时支持 GET 和 POST：GET 把参数放在查询串，POST 把同名参数放在 JSON 请求体，语义完全相同。传大批 `user_ids` 时用 POST。
- 多值参数：GET 用英文逗号分隔，POST 用 JSON 数组。空字符串视为未提供。
- 时间为 RFC 3339，响应统一输出 UTC。`day` 为 `YYYY-MM-DD`，按 Asia/Shanghai 划分，与轨迹接口一致。
- 编码（`intent_code`、`error_code`）一律取自 `/taxonomy` 返回的 `code`，区分大小写。
- 取不到的值返回 `null`，不补 0；数组无记录返回 `[]`；对象字段全部固定返回。

### 1.4 成功响应

所有 200 响应统一为：

```json
{
  "request_id": "req_01ABC",
  "schema_version": "1.0",
  "data": {},
  "meta": {
    "taxonomy_version": "2026-10",
    "data_updated_at": "2026-11-02T02:00:00Z",
    "filters": {}
  }
}
```

- `taxonomy_version`：本次返回的编码所属的分类版本。
- `data_updated_at`：分析结果最近一次更新的时间，看板据此显示“数据截至”。
- `filters`：回显实际生效的筛选条件。
- 响应可以新增字段，但不得删除字段、改变类型或含义；破坏性变更使用 `/v2/`。

## 2. 共用筛选参数

`/summary` 和 `/traces` 使用同一套筛选参数和语义。要求：`/summary` 里任一分组的 `traces`，等于用该分组的键补充筛选后调用 `/traces` 得到的 `total`。看板的上卷、下钻和查明细都依赖这一点。

| 参数 | 类型 | 必填 / 默认 | 语义 |
| --- | --- | --- | --- |
| `dataset` | enum | 必填 | `daily`（国内）/ `overseas`（海外），与轨迹接口一致 |
| `source` | enum，可多值 | 默认全部 | `feedback` 数据回流分析；`prelaunch` 上线前分析 |
| `start_day` / `end_day` | `YYYY-MM-DD` | 可选 | trace 所属日期，两端都包含 |
| `intent` | 编码，可多值 | 可选 | trace 的意图属于其中任一编码，或其任一子孙分类 |
| `error` | 编码，可多值 | 可选 | trace 至少命中其中一个编码，或其任一子孙分类 |
| `has_error` | boolean | 可选 | `true` 命中任意问题；`false` 未命中任何问题 |
| `app_version` | string，可多值 | 可选 | 产生该 trace 的应用版本 |
| `user_ids` | string，可多值 | 可选 | trace 的发起用户属于这批用户；单次至少支持 5000 个 |
| `taxonomy_version` | string | 默认当前版本 | 按该版本解释 `intent`、`error`，返回的编码也属于该版本 |

组合规则：

- 不同参数之间是“且”，同一参数的多个值之间是“或”。例如 `intent=A&error=B,C` 表示“意图属于 A，并且命中了 B 或 C”。
- 传大类编码时，由分析组按分类树展开到全部子孙，看板不自己拼编码前缀。
- 只统计分析过的 trace，每条取最新一版分析结果（见第 8 节）。
- 未知的编码、枚举值返回 422，不静默返回空集。

## 3. GET /taxonomy

返回意图或问题的分类树。看板用它把编码翻译成名称，并把细分类汇总到大类。

| 参数 | 类型 | 必填 / 默认 | 语义 |
| --- | --- | --- | --- |
| `kind` | enum | 必填 | `intent` 意图；`error` 问题 |
| `version` | string | 默认当前版本 | 指定分类版本 |

### data

```json
{
  "kind": "error",
  "version": "2026-10",
  "status": "current",
  "released_at": "2026-10-15T00:00:00Z",
  "versions": [
    {"version": "2026-10", "status": "current", "released_at": "2026-10-15T00:00:00Z"},
    {"version": "2026-09", "status": "deprecated", "released_at": "2026-09-10T00:00:00Z"}
  ],
  "nodes": [
    {"code": "data", "label": "数据问题", "parent_code": null, "level": 1, "order": 1,
     "definition": "回答所用数据有误或缺失", "counts_as_error": true},
    {"code": "data.stale_quote", "label": "行情数据过期", "parent_code": "data", "level": 2, "order": 1,
     "definition": "回答使用了非最新的行情数据", "counts_as_error": true}
  ]
}
```

- `nodes` 是该版本的全部节点，层级不限。`level` 从 1 开始，顶层节点的 `parent_code` 为 `null`。
- `code` 在同一 `kind`、同一版本内唯一。同一个 `code` 在不同版本间含义不变；含义变了必须换新 `code`。
- `order` 是同一上级下的展示顺序。
- `counts_as_error` 只对 `kind=error` 有意义，默认 `true`。如果某些问题编码只是提示、不算错误，标为 `false`；`has_error` 和 `error_traces` 只统计 `counts_as_error=true` 的编码。`kind=intent` 时返回 `null`。
- `versions` 列出该 `kind` 的全部版本，按发布时间倒序。

## 4. GET|POST /summary

先按第 2 节的条件筛选，再按一到两个维度分组计数。意图分布、问题分布、错误占比、交叉矩阵、每日趋势都由这一个接口提供。

### 参数

第 2 节全部参数，加上：

| 参数 | 类型 | 必填 / 默认 | 语义 |
| --- | --- | --- | --- |
| `group_by` | enum，1–2 个 | 必填 | 分组维度：`intent`、`error`、`day`、`user`、`app_version`、`source` |
| `level` | enum | 默认 `top` | 只对 `intent`、`error` 维度生效。`top` 按顶层大类；`leaf` 按最细一级；`children` 按筛选值的下一级展开 |
| `sort` | enum | 见下 | `traces`、`users`、`rate`，降序 |
| `limit` | integer | 默认 100，最大 1000 | 每页返回的分组数 |
| `cursor` | string | 首次不传 | 分组超过 `limit` 时翻页 |

- `level=children` 要求同一维度恰好筛了一个编码，例如 `intent=A&group_by=intent&level=children` 返回 A 的各个子类。
- 两个维度都是 `intent`/`error` 时，`level` 同时作用于两者。
- 排序：`group_by` 含 `day` 时默认按 `day` 升序，其余情况默认按 `traces` 降序。`rate` = `traces / analyzed`。

### data

```json
{
  "total": {"analyzed": 1826, "traces": 1826, "users": 1204, "error_traces": 731},
  "groups": [
    {"keys": {"intent": "market"}, "analyzed": 612, "traces": 612, "users": 498, "error_traces": 270},
    {"keys": {"intent": "stock"}, "analyzed": 455, "traces": 455, "users": 380, "error_traces": 151},
    {"keys": {"intent": null}, "analyzed": 12, "traces": 12, "users": 12, "error_traces": 3}
  ],
  "next_cursor": null,
  "has_more": false
}
```

| 字段 | 含义 |
| --- | --- |
| `keys` | 分组键，键名即 `group_by` 的维度名。`user` 维度的键名为 `user_id` |
| `traces` | 满足全部筛选条件、且落在该组的 trace 数 |
| `users` | 这些 trace 的去重 `user_id` 数，`user_id` 为空的不计 |
| `error_traces` | 其中命中任意问题（`counts_as_error=true`）的 trace 数 |
| `analyzed` | 占比的分母，算法见下 |
| `total` | 同一筛选范围、不分组时的四个数 |

### 分母 `analyzed` 的算法

计算 `analyzed` 时：去掉 `error`、`has_error` 两个筛选条件，并忽略分组键里的 `error` 维度，其余筛选条件和分组键不变。这样 `traces / analyzed` 始终表示“在该组分析过的 trace 里，有多大比例命中了这个问题”，而不会因为筛了问题就变成 100%。

| 调用 | 某一组的 `analyzed` | `traces / analyzed` 的含义 |
| --- | --- | --- |
| `intent=A&group_by=error` | 意图 A 下分析过的 trace 数，各组相同 | 意图 A 里命中该问题的比例 |
| `error=B&group_by=intent` | 该意图下分析过的 trace 数 | 该意图里命中 B 的比例 |
| `group_by=intent,error` | 该行意图下分析过的 trace 数 | 该意图里命中该问题的比例 |
| `error=B&group_by=day` | 当天分析过的 trace 数 | 当天命中 B 的比例 |
| `group_by=intent`（不筛问题） | 等于 `traces` | 用 `error_traces / analyzed` 得到该意图的错误占比 |

`total.analyzed` 同理：去掉 `error`、`has_error` 后整个筛选范围内分析过的 trace 数。

## 5. GET|POST /traces

按第 2 节的条件列出 trace，每条直接带摘要。点击 `/summary` 的任一分组时，看板把该组的键作为筛选条件调用本接口。

### 参数

第 2 节全部参数，加上：

| 参数 | 类型 | 必填 / 默认 | 语义 |
| --- | --- | --- | --- |
| `q` | string | 可选 | 在问句上按字面子串匹配，忽略大小写，最多 200 字符 |
| `page_size` | integer | 默认 20，范围 1–100 | 每页条数 |
| `cursor` | string | 首次不传 | 翻页 |
| `ids_only` | boolean | 默认 `false` | `true` 时只返回 trace\_id，`page_size` 上限放宽到 5000，用于导出 |

- 排序固定为 `(asked_at DESC, trace_id DESC)`。
- `cursor` 不透明，绑定首次请求的筛选条件和 `page_size`，至少保留 30 分钟；过期返回 410。翻页期间新增的分析结果可以不出现，但已有记录不得重复或遗漏。

### data

```json
{
  "items": [
    {
      "trace_id": "trace_01ABC",
      "day": "2026-10-21",
      "asked_at": "2026-10-21T02:10:00Z",
      "source": "feedback",
      "user_id": "u_8f3a",
      "app_version": null,
      "query_preview": "英伟达今天为什么跌",
      "intent_code": "stock.move_reason",
      "error_codes": ["data.stale_quote"],
      "has_error": true,
      "analysis_id": "an_01XYZ",
      "analyzed_at": "2026-10-22T03:00:00Z"
    }
  ],
  "total": 412,
  "page_size": 20,
  "next_cursor": "cur_01XYZ",
  "has_more": true
}
```

- `total` 是当前筛选下的准确总数，必须与 `/summary` 对应分组的 `traces` 相等。
- `error_codes` 为最细一级编码，没有命中时为 `[]`；`intent_code` 同样为最细一级，未分出意图时为 `null`。
- `query_preview` 最多 160 个字符。
- `app_version`、`user_id` 没有时为 `null`。
- `ids_only=true` 时 `items` 为 trace\_id 字符串数组。
- 最后一页 `next_cursor=null`、`has_more=false`；空集 `items=[]`、`total=0`。

## 6. POST /traces/batch

按一批 trace\_id 取摘要。用于看板已经拿到 trace\_id（例如来自业务侧对话列表、自进化批次）时补上分析结果。

### 请求体

```json
{
  "dataset": "overseas",
  "trace_ids": ["trace_01ABC", "trace_01ABD"],
  "taxonomy_version": null
}
```

- `trace_ids` 单次最多 1000 个。
- `taxonomy_version` 可选，默认当前版本。

### data

```json
{
  "items": [
    {"trace_id": "trace_01ABC", "status": "analyzed", "day": "2026-10-21", "...": "其余字段同 /traces 的 items"},
    {"trace_id": "trace_01ABD", "status": "not_analyzed", "day": null, "intent_code": null, "error_codes": [], "has_error": null}
  ]
}
```

- 返回顺序与请求中的 `trace_ids` 一致，每个请求的 id 都有且只有一条。
- `status`：`analyzed` 已分析；`not_analyzed` 未分析或分析组不认识该 id。未分析时分析类字段为 `null`，`error_codes` 为 `[]`。
- 不要因为未分析就丢掉该条，看板需要用它统计分析覆盖率。

## 7. GET /traces/{trace\_id}

返回单条 trace 的完整内容、每个问题的说明与引用位置，以及历史分析记录。看板的 trace 详情页用它高亮问题所在的步骤。

| 参数 | 类型 | 必填 / 默认 | 语义 |
| --- | --- | --- | --- |
| `dataset` | enum | 必填 | 同第 2 节 |
| `day` | `YYYY-MM-DD` | 视 trace\_id 是否全局唯一而定 | trace\_id 只在单日内唯一时必填 |
| `taxonomy_version` | string | 默认当前版本 | 同第 2 节 |

### data

```json
{
  "trace_id": "trace_01ABC",
  "day": "2026-10-21",
  "asked_at": "2026-10-21T02:10:00Z",
  "source": "feedback",
  "user_id": "u_8f3a",
  "app_version": null,
  "intent_code": "stock.move_reason",
  "error_codes": ["data.stale_quote"],
  "has_error": true,
  "analysis_id": "an_01XYZ",
  "analyzed_at": "2026-10-22T03:00:00Z",
  "analyzer": "qwen3.5-122b / prompt v7",
  "query": "英伟达今天为什么跌",
  "final_output": "……",
  "steps": [
    {"index": 0, "type": "generation", "name": "plan", "content": "……"},
    {"index": 3, "type": "tool", "name": "get_quote", "content": "……"}
  ],
  "summary": "回答引用了前一交易日的收盘价。",
  "errors": [
    {"code": "data.stale_quote", "message": "工具返回的是 10-20 收盘价，回答当作实时价格",
     "refs": [{"step_index": 3, "text": "close: 138.2"}]}
  ],
  "history": [
    {"analysis_id": "an_01XYW", "analyzed_at": "2026-10-21T20:00:00Z", "analyzer": "qwen3.5-122b / prompt v6",
     "taxonomy_version": "2026-09", "intent_code": "stock.move_reason", "error_codes": []}
  ]
}
```

- 从 trace\_id 到 analyzed\_at 的字段与 `/traces` 的 items 相同，只是用完整的 query 代替 query\_preview。
- `analyzer`：产出这版结果的模型与 prompt 版本，人工标注写 `human`。
- `errors`：每个命中的问题一项。`refs` 为引用位置，`step_index` 与 `text` 至少给一个；给不出引用时为 `[]`。
- `history`：该 trace 更早的分析版本，按 `analyzed_at` 倒序；只分析过一次时为 `[]`。
- `query`、`final_output`、`steps` 是对话正文。如果正文不由分析组保存，这三个字段返回 `null`，看板改从轨迹接口取；此时 `step_index` 必须与轨迹接口的步骤序号一致。
- trace 不存在或未分析返回 404。

## 8. 统计口径约定

以下口径对 `/summary` 和 `/traces` 同时生效。

1. **只算分析过的 trace**：未分析的 trace 不进入任何计数，也不进入分母。
2. **每条 trace 只取最新一版分析**：重新分析后，旧结果只出现在 `/traces/{trace_id}` 的 `history` 里。
3. **一条 trace 命中多个问题**：按 `error` 分组时，它在命中的每个问题组里各计一次，所以各组 `traces` 之和可以大于 `total.traces`。按大类分组时，同一大类下命中的多个子问题只计一次。
4. **一条 trace 只有一个意图**：按 `intent` 分组时，各组 `traces` 之和等于 `total.traces`。未分出意图的 trace 进入 `intent` 为 `null` 的组。如果你们的分析会给一条 trace 打多个意图，请在第 11 节告知。
5. **大类展开**：筛选参数传大类编码时，包含其下所有层级的子类，按分析组的分类树展开。
6. **“有错误”**：命中至少一个 `counts_as_error=true` 的问题编码。`has_error`、`error_traces` 都按此判断。
7. **分类版本**：返回的编码必须属于 `meta.taxonomy_version`。按旧版本分析的结果由分析组映射到请求的版本；映射不了的进入编码为 `null` 的组，不得丢弃。
8. **一致性**：`/summary` 任一分组的 `traces`，等于用该分组的键补充筛选后 `/traces` 的 `total`。同一时刻两个接口必须基于同一份分析结果。

## 9. 常见查询示例

看板的主要场景都由第 2 节的筛选加 `group_by` 组合得到。下表省略了必填的 `dataset`。

| 场景 | 调用 | 取数 |
| --- | --- | --- |
| 每日分析量与错误占比 | `GET /summary?group_by=day` | `error_traces / analyzed` |
| 意图分布（大类） | `GET /summary?group_by=intent` | `traces / total.analyzed` |
| 问题分布（大类） | `GET /summary?group_by=error` | `traces / analyzed` |
| 意图 A 下各问题的占比 | `GET /summary?intent=A&group_by=error` | `traces / analyzed` |
| 问题 B 出现在哪些意图 | `GET /summary?error=B&group_by=intent` | 各意图里命中 B 的比例 = `traces / analyzed` |
| 意图 × 问题交叉矩阵 | `GET /summary?group_by=intent,error` | 每格 `traces / analyzed` |
| 问题 B 的每日趋势 | `GET /summary?error=B&group_by=day` | `traces / analyzed` |
| 问题热力条（日 × 问题） | `GET /summary?group_by=day,error` | 每格 `traces` |
| 展开意图 A 的子类 | `GET /summary?intent=A&group_by=intent&level=children` | — |
| 同时是意图 A、问题 B 的 trace | `GET /traces?intent=A&error=B` | 列表 |
| 某用户组的意图分布与错误占比 | `POST /summary`，请求体带 `user_ids` 和 `group_by: ["intent"]` | `error_traces / analyzed` |
| 单个用户遇到的问题 | `GET /summary?user_ids=u1&group_by=error`，再 `GET /traces?user_ids=u1` | — |
| 上线前两个版本对比 | `GET /summary?source=prelaunch&app_version=v1,v2&group_by=app_version,error` | 同一问题在两个版本的 `traces / analyzed` |

```json
      {"keys": {"intent": "stock"}, "analyzed": 455, "traces": 45, "users": 41, "error_traces": 45}

    "has_more": false
  },
  "meta": {
    "taxonomy_version": "2026-10",
    "data_updated_at": "2026-11-02T02:00:00Z",
    "filters": {"dataset": "overseas", "error": ["data.stale_quote"]}
  }
}
```

读法：行情数据过期共出现在 143 条 trace 里。市场类意图分析了 612 条，其中 98 条命中，占 16.0%；个股类意图 455 条中 45 条命中，占 9.9%。

## 10. 错误响应

非 200 响应统一为 JSON，认证失败也不例外：

```json
{
  "request_id": "req_01ABC",
  "error": {
    "code": "INVALID_ARGUMENT",
    "message": "group_by 最多两个维度",
    "details": {"param": "group_by"}
  }
}
```

| HTTP | code | 场景 |
| --- | --- | --- |
| 400 | `INVALID_ARGUMENT` | 参数格式错误；`group_by` 为空或超过两个；`level=children` 但该维度未恰好筛一个编码；`start_day` 晚于 `end_day` |
| 401 | `UNAUTHENTICATED` | 认证失败 |
| 404 | `NOT_FOUND` | trace 不存在或未分析；分类版本不存在 |
| 410 | `CURSOR_EXPIRED` | cursor 过期，客户端从第一页重新开始 |
| 413 | `TOO_MANY_IDS` | `user_ids` 或 `trace_ids` 超过上限，`details` 里给出上限 |
| 422 | `UNKNOWN_CODE` | `intent`、`error` 编码不在指定版本的分类中，`details` 里列出未知编码 |
| 503 | `UNAVAILABLE` | 服务暂时不可用 |

## 11. 需要分析组确认的事项

以下问题的答案会影响字段含义或看板的展示方式，请在实现前回复。

| # | 问题 | 影响 |
| --- | --- | --- |
| 1 | trace\_id 是否与轨迹接口是同一套？全局唯一，还是只在 `(dataset, day)` 内唯一？ | 决定看板能否把分析结果挂回对话正文，以及详情接口是否必须传 `day` |
| 2 | trace 上的 user\_id 是否与业务侧的用户标识一致（或使用同一套脱敏映射）？ | 不一致则 `user_ids` 筛选无法使用 |
| 3 | 回流 trace 是怎么挑选的：全量、随机抽样，还是按规则挑可疑对话？每天覆盖多少比例？ | 按规则挑选时错误占比会偏高；建议在 `meta` 加 `sampling` 说明 |
| 4 | 上线前分析的 trace 是否都带 `app_version`？是否还需要 benchmark 名称和版本？ | 决定上线前分析能否与发版对应 |
| 5 | 一条 trace 是否可能有多个意图？ | 如果是，第 8 节第 4 条和意图分组的口径需要重定 |
| 6 | 是否存在不算错误的问题编码（如提示级）？ | 决定 `counts_as_error` 的取值 |
| 7 | 分类升版后，旧版本的分析结果是重新分析，还是按映射表转换？ | 决定跨版本趋势是否可比 |
| 8 | 对话正文由分析组返回，还是看板从轨迹接口取？引用位置用步骤序号还是文本片段？ | 决定第 7 节正文字段和 `refs` 的形式 |
| 9 | `user_ids`、`trace_ids` 单次上限；分析结果多久更新一次、相对对话发生时间延迟多久？ | 决定看板的分批策略和“数据截至”的展示 |

## 12. 验收用例

看板接入时逐条执行以下检查，全部通过视为实现完成。

1. **分类树完整**：`/taxonomy` 里每个非空 `parent_code` 都能在同一版本的 `nodes` 中找到。
2. **分组与明细一致**：对 `/summary?group_by=intent,error` 随机取 5 个分组，用其键作为 `intent`、`error` 调用 `/traces`，`total` 均等于该组的 `traces`。
3. **分母规则**：`/summary?intent=A&group_by=error` 各组的 `analyzed` 相等，且等于 `/summary?intent=A&group_by=intent&level=top` 中 A 所在组的 `analyzed`。
4. **错误占比**：不带筛选时的 `total.error_traces`，等于 `/summary?has_error=true` 的 `total.traces`。
5. **意图互斥**：`/summary?group_by=intent&level=leaf` 各组 `traces` 之和等于 `total.traces`。
6. **多问题计数**：取一条命中两个不同叶子问题的 trace，它同时出现在 `/traces?error=<问题1>` 和 `/traces?error=<问题2>` 的结果中。
7. **大类展开**：`/traces?intent=<大类>` 的 `total`，等于其各个直接子类分别查询的 `total` 之和（前提是意图只打在叶子分类上）。
8. **未知编码**：`/summary?intent=not_exist&group_by=day` 返回 422 `UNKNOWN_CODE`。
9. **批量查询**：`/traces/batch` 传入 1 个已分析 id 和 1 个虚构 id，返回 2 条、顺序不变，虚构 id 标为 `not_analyzed`。
10. **重分析**：对一条 trace 重新分析后，`/summary` 只按新结果计数，旧结果出现在详情的 `history` 里。
11. **导出**：同一筛选下 `ids_only=true` 翻页得到的 trace\_id 集合，与普通翻页得到的集合相同。
12. **用户筛选**：`POST /summary` 传入 5000 个 `user_ids` 正常返回；结果里所有 trace 的 `user_id` 都属于这批用户。

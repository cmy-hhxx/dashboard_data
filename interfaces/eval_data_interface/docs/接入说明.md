# 接入说明（给消费方，v2.0）

服务：`eval_data_interface`，对话分析查询接口的 AIME 实现。只读，无认证。
v2 是**破坏性改版**：去掉了所有“错误/对错”判定语义，改为直接暴露 trace 上的问题条目与
P0–P4 严重度，并新增一个专门数严重度的接口。v1 → v2 的逐字段映射见
[v2 变更说明](v2-变更说明.md)。

| 部署 | 对外 | 集群内 | 数据 |
|---|---|---|---|
| 弗吉尼亚 | `http://10.217.219.2:2224/api/v1/analysis` | `http://interactive-npasm9ch66eb:5003/api/v1/analysis` | AIME |
| 乌兰察布 | 暂未提供（问财供数接口尚未实现，5003 已停用） | — | — |

健康检查 `GET /healthz`（`ok` / `building` / `traces` / `problems` / `data_updated_at`）。
5003 目前只部署在弗吉尼亚；部署与端口映射见 [接口使用指南](../../../docs/接口使用指南.md) 第零节。

请求头：`Accept: application/json`；POST 另带 `Content-Type: application/json`。
所有 200 响应统一为 `{request_id, schema_version: "2.0", data, meta}`。`meta` 里有
`taxonomy_version`、`taxonomy_versions`（`intent` / `problem` / `severity` 三套版本）、
`data_updated_at`、`built_at`、`filters`（实际生效的筛选条件回显）。

## 先理解三件事

1. **问题条目（problem）**：归因数据里 `turns[].problem[]` 的一项，带 `label`、`severity`、
   `component`、`evidence`。一条 trace 可以命中多个问题。
2. **严重度**：`P0`–`P4`，P0 最重、P4 最轻。它是问题条目自带的定级，**不是对错判定**。
3. **问题编码（code）**：聚类流水线给问题条目映射的 `S9.M5.1` 这类编码。只有被聚类过的问题
   才有编码，未聚类的 `code` 为 `null`；未聚类问题仍然有严重度、仍然计入所有问题数与 P0–P4 统计。
   聚合按 `problem` 分组时，未聚类问题落在 `problem: null` 组。

“对不对”用 `is_correct` 表示（`true` / `false` / `null`）。数据里目前没有标准答案，
**恒为 `null`**；接口不做对错统计，也不再用 `has_error` 之类字段替数据下结论。

## 通用筛选参数

`/summary`、`/severity`、`/traces` 共用：

| 参数 | 类型 | 语义 |
|---|---|---|
| `dataset` | 必填 | 只有 `aime_eval`；传 `daily` / `overseas` 返回 422 |
| `source` | 多值 | `prelaunch`（日常）/ `feedback`（流失回流） |
| `start_day` / `end_day` | `YYYY-MM-DD` | trace 所属日期，两端都包含 |
| `intent` | 多值编码 | 意图属于任一编码或其子孙 |
| `problem` | 多值编码 | 命中任一问题编码或其子孙 |
| `severity` | 多值，`P0`–`P4` | 至少命中一个该严重度的问题 |
| `app_version` | 多值 | `AIME-Atlas_expert` 等 |
| `user_ids` | 多值 | 单次最多 5000 |
| `taxonomy_version` | 单值 | 默认当前版本 |

- GET 多值用英文逗号，POST 用 JSON 数组；空字符串视为未提供。
- 不同参数之间是「且」，同参数多值之间是「或」。
- 传大类编码（`T01`、`S9`、`S9.M5`）会自动展开到全部子孙；未知编码 / 未知严重度返回 422。
- `user_ids` 超过 5000 → 413。

## 1. 分类树

```http
GET /api/v1/analysis/taxonomy?kind=intent
GET /api/v1/analysis/taxonomy?kind=problem&app_version=AIME-Atlas_expert
GET /api/v1/analysis/taxonomy?kind=severity
```

`data.nodes[]` 每项：`code`、`label`、`parent_code`、`level`、`order`、`definition`。

- `intent`：27 个顶层任务 + 169 个子任务，版本 `2026-10`。
- `problem`：聚类树，按 `app_version` 选树（expert / fast 两棵，当前 `4.2.0`）。
- `severity`：固定 P0–P4，按 `order` 从重到轻：

| code | definition |
|---|---|
| P0 | 确认有剩余影响，程度最重 |
| P1 | 确认有剩余影响 |
| P2 | 确认有剩余影响 |
| P3 | 确认有剩余影响，程度最轻 |
| P4 | 过程缺陷已恢复，未进入交付 |

## 2. 聚合

```http
GET /api/v1/analysis/summary?dataset=aime_eval&group_by=intent
POST /api/v1/analysis/summary
{"dataset":"aime_eval","group_by":["intent","problem"],"app_version":["AIME-Atlas_expert"],"user_ids":["u1","u2"]}
```

参数：`group_by`（1–2 个：`intent`、`problem`、`day`、`user`、`app_version`、`source`）、
`level`（`top`/`leaf`/`children`）、`sort`（`traces`/`users`/`problems`/`rate`）、
`limit`（默认 100，最大 1000）、`cursor`。

```json
{
  "data": {
    "total": {"analyzed": 18012, "traces": 15504, "users": 3211,
              "problem_traces": 15504, "problems": 10942},
    "groups": [
      {"keys": {"intent": "T01"}, "analyzed": 1683, "traces": 1683, "users": 901,
       "problem_traces": 1120, "problems": 1874}
    ],
    "next_cursor": null,
    "has_more": false
  }
}
```

- `traces`：满足全部筛选的 trace 数；`users`：去重用户数。
- `problem_traces`：其中至少有一个问题条目的 trace 数。
- `problems`：这些问题条目总数的**问题条目数**（一条 trace 可贡献多个）。
- `analyzed` 是分母：去掉 `problem` / `severity` 筛选、并忽略分组键里的 `problem` 维度后的 trace 数。
- 按 `problem` 分组时，一条 trace 的不同问题条目会进各自的编码组：`traces` 之和可能大于
  `total.traces`，但每个问题条目只归一个组，所以各组 `problems` 之和恒等于 `total.problems`。
  未聚类问题进 `{"problem": null}` 组；没有问题的 trace 不进入任何 problem 分组。
  `level=top` 时按环节归并，`level=children` 时按筛选值的下一层归并。

## 3. 严重度统计（新增）

```http
GET /api/v1/analysis/severity?dataset=aime_eval
GET /api/v1/analysis/severity?dataset=aime_eval&group_by=day
GET /api/v1/analysis/severity?dataset=aime_eval&app_version=AIME-Atlas_expert&group_by=problem
```

参数：通用筛选 + `group_by`（0–2 个，可省略）、`level`（`top`/`leaf`/`children`，
只作用于 `problem` 维度，默认 `top`）、`sort`、`limit`、`cursor`。

```json
{
  "data": {
    "total": {
      "analyzed": 18012,
      "traces": 15504,
      "problems": 10942,
      "severity": {
        "P0": {"problems": 12, "traces": 12},
        "P1": {"problems": 345, "traces": 300},
        "P2": {"problems": 1200, "traces": 900},
        "P3": {"problems": 2500, "traces": 2100},
        "P4": {"problems": 6885, "traces": 5200}
      },
      "unlabeled": 0
    },
    "groups": [
      {"keys": {"day": "2026-10-21"}, "analyzed": 612, "traces": 530, "problems": 701,
       "severity": {"P0": {"problems": 1, "traces": 1}, "P1": {"problems": 9, "traces": 8},
                    "P2": {"problems": 66, "traces": 60}, "P3": {"problems": 130, "traces": 120},
                    "P4": {"problems": 495, "traces": 400}}, "unlabeled": 0}
    ],
    "next_cursor": null,
    "has_more": false
  }
}
```

- `severity.Pn.problems`：命中的该等级问题条目数——**“有多少个 P0”用这个**。
- `severity.Pn.traces`：至少有一个该等级问题的 trace 数。
- `problems` 是所有等级条目之和；`unlabeled` 是严重度缺失（不在 P0–P4）的条目数。
- 一条 trace 可以同时出现在多个等级里（它可能有多个不同等级的问题），所以各等级 `traces` 之和
  可以大于 `total.traces`；但各等级 `problems` 之和恒等于 `problems`（每个条目只有一个等级）。
- `group_by=problem` 时规则同 `/summary`：每个问题条目只归一个组，各组 `problems` 之和等于总数。
- 不给 `group_by` 时 `groups` 为 `[]`，只返回 `total`。
- 想看“是哪些 trace”：用 `GET /traces?severity=P0`（见下一节），列表里每条带它的问题条目。

## 4. trace 列表

```http
GET /api/v1/analysis/traces?dataset=aime_eval&severity=P0,P1&page_size=20
```

参数：通用筛选 + `page_size`（默认 20，最大 100；`ids_only=true` 时最大 5000）、`cursor`、`ids_only`。
排序固定 `(asked_at DESC, trace_id DESC)`。

`items[]`：

```json
{
  "trace_id": "d4806fd5…", "day": "2026-10-23", "asked_at": "2026-10-23T02:10:00Z",
  "source": "prelaunch", "user_id": "xutianhao", "session_id": "thread_19de1b23…",
  "app_version": "AIME-Atlas_expert", "query_preview": "英伟达今天为什么跌", "intent_code": "T01.S02",
  "is_correct": null, "problem_count": 2, "problem_codes": ["S9.M5.1"],
  "problems": [
    {"code": "S9.M5.1", "label": "旧数据当当前值", "severity": "P2",
     "component": "answer_synthesis", "session_level": false},
    {"code": null, "label": "自由文本问题", "severity": "P4",
     "component": "answer_synthesis", "session_level": true}
  ],
  "analysis_id": "an_…", "analyzed_at": "2026-11-02T…Z"
}
```

- `problems` 是精简问题数组：`code`（未聚类为 `null`）、`label`、`severity`、`component`、
  `session_level`；完整定义、原因与证据去详情接口拿。
- `problem_codes` 是已聚类编码去重排序；`problem_count` 等于 `problems` 长度。
- `session_id` 用于拼样本详情页链接（见下一节）；数据里没有时为 `null`。
- `total` 恒等于 `/summary` 对应分组的 `traces`。
- trace_id **不全局唯一**（同一 id 可能跨模型或重跑出现多次，详情接口要求带 `day`）。
  `ids_only=true` 按 trace 逐条返回，同一 id 可能出现多次，导出时按需去重。

## 5. 批量取摘要

```http
POST /api/v1/analysis/traces/batch
{"dataset": "aime_eval", "trace_ids": ["trace_a", "trace_b"]}
```

最多 1000 个 id，返回顺序与请求一致，每个 id 一条；不认识的 id 标 `status: "not_analyzed"`，
分析字段为 `null`、`problem_codes` / `problems` 为 `[]`、`problem_count` 为 `0`。
已分析的条目字段与 `/traces` 的 `items` 相同（含 `session_id`），额外带 `status: "analyzed"`；
未分析条目 `session_id` 为 `null`。

## 6. 单条详情

```http
GET /api/v1/analysis/traces/{trace_id}?dataset=aime_eval&day=2026-10-23
```

`day` **必填**（trace_id 只在单日内唯一，同一天重跑取最新一版）。字段：

- 与 `/traces` item 相同的摘要字段（含 `problems` 精简数组、`is_correct`）。
- `session`：`eval_input` 整行；`trace`：命中的 trace 对象（结构同轨迹接口）。
- `analysis.problems[]`：完整问题条目：

```json
{"code": "S9.M5.1", "label": "旧数据当当前值", "severity": "P2", "definition": "…",
 "phenomena": "…", "reason": "…", "component": "answer_synthesis",
 "evidence": [{"position": "trace_index 0 / message_index 16 / path /content", "quote": "…"}],
 "session_level": false}
```

- `analysis.is_correct`：`true` / `false` / `null`（无标准答案）。
- `analysis.history[]`：同一 trace 更早的分析行，`problem_codes` 为当时的编码列表。
- trace 不存在或未分析 → 404。

## 跳到样本详情页（5002）

问题列表里每条 trace 都能直接跳到对应的对话详情页，并按 trace 定位到会话里的那一轮：

```text
https://rtahz.10jqka.com.cn/bmtp/proxy/dsw/trace-detail-oversea/?product=aime&case=<split>|<model>|<session_id>&trace=<trace_id>
```

| 页面参数 | 从 5003 字段拼接 |
|---|---|
| `product` | 固定 `aime` |
| `case` | `split` + `model` + `session_id`：`source=prelaunch` → `daily`、`feedback` → `lost`；`app_version` 后缀 `_expert` → `aime_expert`、`_fast` → `aime_fast` |
| `trace` | `/traces` item 的 `trace_id`（即 `/traces/{id}` 里 `attribution.turns[].trace_id` 的同一套 ID） |

示例：

```bash
curl -s "http://<目标环境>:<5003 对外端口>/api/v1/analysis/traces?dataset=aime_eval&severity=P0&page_size=1" \
  | jq -r '.data.items[0] | [.trace_id, .session_id, .source, .app_version] | @tsv'
```

- 页面会选中 `trace` 对应的轮次并滚动过去；找不到该 trace 时页面明确报错（不会静默停在别的轮）。
- JSON 定位：`/api/context?product=&case=&trace=` 会回显 `trace`；轮次位置用
  `/samples/<slug>.json` 的 `attribution.turns[].trace_id` 自行匹配（页面就是这么做的）。

## 分页与 cursor

`cursor` 是不透明字符串，绑定首次请求的筛选条件、`group_by`、`sort`、`page_size`；
30 分钟内有效，过期返回 410 `CURSOR_EXPIRED`（从第一页重来）。
翻页期间新增的分析结果可能不出现，但已有记录不会重复或遗漏。

## 错误

| HTTP | code | 场景 |
|---|---|---|
| 400 | `INVALID_ARGUMENT` | 参数格式错、`group_by` 为空/超过 2 个、`level=children` 未恰好筛一个编码、`start_day > end_day`、缺 `day` |
| 404 | `NOT_FOUND` | trace 不存在或未分析、分类版本不存在 |
| 410 | `CURSOR_EXPIRED` | cursor 过期 |
| 413 | `TOO_MANY_IDS` | `user_ids` > 5000、`trace_ids` > 1000 |
| 422 | `UNKNOWN_CODE` | 未知编码、未知严重度或枚举值 |
| 503 | `UNAVAILABLE` | 索引还在构建（看 `/healthz` 的 `building`） |

## 数据新鲜度

`meta.data_updated_at` 是最新一批分析结果的更新时间；服务每 10 分钟增量重建索引。
页面上的“数据截至”用这个字段。索引结构升级（v1 → v2）后首轮会全量重建归因索引，
`/healthz` 的 `building` 为 `true` 时返回 503。

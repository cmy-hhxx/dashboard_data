# 协议落地说明：与 v1 协议的差异、v2 口径与 §11 答复

对应文档：`docs/对话分析查询接口协议 v1.0.md`。实现已升级到 **schema 2.0**
（v1 → v2 的逐字段映射见 [v2 变更说明](v2-变更说明.md)），对外接口以
[接入说明](接入说明.md) 为准。本文件记录与 v1 协议的偏离、口径原因，以及协议第 11 节
「需要分析组确认的事项」的答复。

## 一、与 v1 协议的差异

| # | v1 协议 | v2 实现 | 原因 |
|---|---|---|---|
| 1 | `dataset` 枚举 `daily` / `overseas` | 只有 `aime_eval` | 本轮只交付 AIME 一份数据；`daily` / `overseas` 传进来返回 422 |
| 2 | `/taxonomy` 只有 `kind` | `kind=problem` 追加 `app_version` 选树；新增 `kind=severity` | expert / fast 各有一棵聚类树；P0–P4 是数据里的定级，需要随接口给出定义 |
| 3 | 详情返回 `query` / `final_output` / `steps` | 返回 `eval_input` 整行（`session`）+ 命中的 `trace` 对象 + `analysis` | 分析组不单独存正文；`eval_input` 的结构体就是看板要渲染的原始数据 |
| 4 | `error` 编码覆盖全部问题 | `problem_codes` 只覆盖被聚类的问题；`problems[]` 覆盖全部问题条目 | 聚类流水线只覆盖部分日期/模型。v2 把“问题条目”和“编码”分开：统计问题数/严重度不依赖聚类 |
| 5 | `is_correct` 之类对错判定 | 不做对错判定；`is_correct` 原样返回（当前恒 `null`） | 数据里没有标准答案，接口不替数据下结论 |
| 6 | `error_traces` / `has_error` | 改为 `problems`（条目数）/ `problem_traces` + `GET /severity` | “发现问题的多少”与“答案对不对”是两件事 |
| 7 | `analysis_id` / `analyzed_at` | 由 `文件 + 行号` 哈希、文件 mtime 生成 | attribution 里没有这两个字段 |
| 8 | cursor 至少保留 30 分钟、过期 410 | 无状态 HMAC 签名 cursor，30 分钟 TTL，密钥落盘 | 服务端零状态，重启/多进程都不失效 |
| 9 | 建议 HTTP Basic + HTTPS | 不做认证 | 平台侧内网 + 固定端口映射；需要时在反向代理加 |
| 10 | GET/POST 同语义 | 一致；`/traces/batch` 只接受 POST | 同协议 |

## 二、§11 的答复

**1. `trace_id` 与轨迹接口是否同一套？全局唯一还是按天唯一？**
同一套。本服务用 `turns[].meta.trace_id`，它与 `eval_input` 里
`traces[].meta.trace_id` 完全一致（10-23 expert 实测 622/622 对上）。
**不全局唯一**：同一 `trace_id` 可能跨 model，也有同一天同一 trace 的重跑多行。
因此详情接口 **必须传 `day`**，同一 `(trace_id, day)` 有多行时取行号最大的那一版，
更早的进 `analysis.history`。

**2. `user_id` 是否与业务侧一致？**
是同一个字段原值（`turns[].meta.user_id`，形如 `xutianhao` / `1913677307`），
未做额外脱敏映射；与 `eval_input` 里的 `user_id` 一致。但没有拿业务侧样本做过核对。

**3. 回流 trace 怎么挑、覆盖多少？**
不是抽样，是整批：`1_lost_user_eval` 目录下的流失用户评测结果按天落盘。
数据里没有采样率字段，`meta` 只回 `source=feedback` 和数据截至时间。
问题数与严重度对这些 trace 而言是“全量”口径。

**4. 上线前 trace 是否都带 `app_version`？**
没有版本字段。`app_version` 由 `turns[].meta.model`（`AIME-Atlas` / `aime-fast-new` 等）
+ 模型目录后缀拼成。benchmark 名称与版本不在数据里，需要另接数据源才能与发版对应。

**5. 一条 trace 是否可能有多个意图？**
否。`task` / `subtask` 各一个值，意图互斥。

**6. 是否存在不算错误的问题编码？**
v1 里这个问题决定 `counts_as_error`；v2 取消了这个判定：P0–P4 全部是问题条目，
接口按严重度原样统计，不再回答“算不算错误”。P4 是「过程缺陷已恢复、未进入交付」。

**7. 分类升版后旧结果怎么处理？**
- 意图：编码固定在 `taxonomy/intent_2026-10.json`，版本 `2026-10`；数据里出现表外
  `task`/`subtask` 时该 trace 的 `intent_code` 为 `null`（不丢 trace）。
- 问题：直接读最新 `cluster_tree.json`，重跑产生新树后整体替换，
  **不保留旧树快照**，因此跨版本趋势不可比。要支持跨版本，需要保留每版树文件并加映射层。

**8. 正文由分析组返回还是看板从轨迹接口取？引用位置用什么？**
正文由本服务从 `eval_input` 返回（`session` 整行 + `trace` 对象），不需要看板二次拼接。
引用位置是 `problem.evidence[]` 里的 `position`（形如
`trace_index 0 / message_index 16 / path /content`）+ `quote`；数据里没有“步骤序号”概念，
未与轨迹接口步骤对齐。session 级问题用 `session_level: true` 标记。

**9. `user_ids` / `trace_ids` 上限、更新延迟？**
上限沿用协议：`user_ids` 5000、`trace_ids` 1000（超过返回 413）。
分析结果按天写入 JSONL，服务每 10 分钟增量重建索引（`REFRESH_SECONDS`），
所以延迟 ≈ 文件落盘时间 + 最多 10 分钟；`meta.data_updated_at` 取最新一版的 `analyzed_at`。

## 三、v2 的统计口径

- **问题条目数**（`problems`）= attribution 里 `turns[].problem[]` 的条数（含 session 级问题），
  与是否被聚类无关。
- **P0–P4**：条目自带的 `severity`，落库为每条 trace 的各等级计数；`GET /severity` 直接读索引。
- **trace 数**：`problem_traces` = 至少一条问题的 trace；`severity.Pn.traces` = 至少一条该等级问题的 trace。
- **编码**：`problem_codes` 只含被聚类的问题；按 `problem` 分组时未聚类问题进 `null` 组。
- **条目缺失严重度**：`/severity` 的 `unlabeled` 单独计数（当前数据为 0）。

## 四、已知缺口（需要后续决策）

1. **意图编码是我们自己的映射**：`task`/`subtask` 是中文自由文本，`T01` / `T01.S02` 由
   `taxonomy/intent_2026-10.json` 固定。如果分析组另有正式编码体系，替换这个 JSON 即可，
   接口不用改。
2. **问题编码依赖聚类覆盖**：未聚类问题只有 `severity` 和 `label`，没有编码。要补编码，
   得让聚类流水线覆盖全部日期/模型，或在 `item_index` 缺条目时回退到 `problem.component_family`。
3. **不做跨版本映射**：聚类树升版后旧结果不会映射到新编码。
4. **`is_correct` 全为 `null`**：数据里这个字段没有填；接口照实返回 `null`，
   等标准答案入库后自动生效，不需要改接口。
5. **问财 / lumi / forecast 不在本服务范围**：`dataset` 只有 `aime_eval`；
   其它产品要各自接一套，或者扩 `dataset` 枚举。

# 协议落地说明：差异、口径与 §11 答复

对应文档：`docs/对话分析查询接口协议 v1.0.md`。
本文件记录实现与协议的偏离（都是因为数据实际形态与协议假设不同），以及协议第 11 节
「需要分析组确认的事项」的答复。

## 一、与协议的差异

| # | 协议 | 实现 | 原因 |
|---|---|---|---|
| 1 | `dataset` 枚举 `daily` / `overseas` | 只有 `aime_eval` | 本轮只交付 AIME 一份数据；`daily` / `overseas` 传进来返回 422 |
| 2 | `/taxonomy` 只有 `kind` | `kind=error` 追加 `app_version` 选树 | 数据里 expert / fast 各有一棵聚类树（196 / 142 节点，不含根；交集 114），一份 `taxonomy_version` 装不下；两棵树的版本都是 `4.1.3` |
| 3 | 详情返回 `query` / `final_output` / `steps` | 返回 `eval_input` 整行（`session`）+ 命中的 `trace` 对象 + `analysis` | 分析组不单独存正文；`eval_input` 的结构体就是看板要渲染的原始数据 |
| 4 | `error` 编码覆盖全部问题 | 只覆盖被聚类的问题（8504 / 10578 轮 ≈ 80%） | 聚类流水线只跑了部分日期/模型；未聚类问题不进 `error_codes`，`has_error` 保持 `false`（已知失真：这 20% 会显示成“无问题”） |
| 5 | `analysis_id` / `analyzed_at` | 由 `文件 + 行号` 哈希、文件 mtime 生成 | attribution 里没有这两个字段 |
| 6 | cursor 至少保留 30 分钟、过期 410 | 无状态 HMAC 签名 cursor，30 分钟 TTL，密钥落盘 | 服务端零状态，重启/多进程都不失效 |
| 7 | 建议 HTTP Basic + HTTPS | 不做认证 | 平台侧内网 + 固定端口映射；需要时在反向代理加 |
| 8 | GET/POST 同语义 | 一致；`/traces/batch` 只接受 POST | 同协议 |

## 二、§11 的答复

**1. `trace_id` 与轨迹接口是否同一套？全局唯一还是按天唯一？**
同一套。本服务用 `turns[].meta.trace_id`，它与 `eval_input` 里
`traces[].meta.trace_id` 完全一致（10-23 expert 实测 622/622 对上）。
**不全局唯一**：10578 轮里 9849 个唯一值；不跨天（0 例），但有 5 个跨 model、
另有 724 例是同一天同一 trace 的重跑多行。因此详情接口 **必须传 `day`**，
同一 `(trace_id, day)` 有多行时取行号最大的那一版，更早的进 `analysis.history`。

**2. `user_id` 是否与业务侧一致？**
是同一个字段原值（`turns[].meta.user_id`，形如 `xutianhao` / `1913677307`），
未做额外脱敏映射；与 `eval_input` 里的 `user_id` 一致。但没有拿业务侧样本做过核对。

**3. 回流 trace 怎么挑、覆盖多少？**
不是抽样，是整批：`1_lost_user_eval` 目录下的流失用户评测结果按天落盘
（2026-09-17～09-27、10-10～10-14）。数据里没有采样率字段，
`meta` 只回 `source=feedback` 和数据截至时间。错误占比对这些 trace 而言是“全量”口径。

**4. 上线前 trace 是否都带 `app_version`？**
没有版本字段。`app_version` 由 `turns[].meta.model`（`AIME-Atlas` / `aime-fast-new`）+ 模型目录
后缀拼成 `AIME-Atlas_expert` / `aime-fast-new_fast`。benchmark 名称与版本不在数据里，
需要另接数据源才能与发版对应。

**5. 一条 trace 是否可能有多个意图？**
否。`task` / `subtask` 各一个值，意图互斥（§8 第 4 条成立）。

**6. 是否存在不算错误的问题编码？**
没有。P0–P4 全部计入错误，`counts_as_error` 恒为 `true`。
如果看板要区分“提示级”，按 `analysis.problems[].severity == "P4"` 过滤即可（P4 占 55.6%）。

**7. 分类升版后旧结果怎么处理？**
- 意图：编码固定在 `taxonomy/intent_2026-10.json`，版本 `2026-10`；数据里出现表外
  `task`/`subtask` 时该 trace 的 `intent_code` 为 `null`（不丢 trace）。
- 问题：直接读最新 `cluster_tree.json`（当前只有 `4.1.3` 一份），重跑产生新树后整体替换，
  **不保留旧树快照**，因此跨版本趋势不可比。要支持跨版本，需要保留每版树文件并加映射层。

**8. 正文由分析组返回还是看板从轨迹接口取？引用位置用什么？**
正文由本服务从 `eval_input` 返回（`session` 整行 + `trace` 对象），不需要看板二次拼接。
引用位置是 `problem.evidence[]` 里的 `position`（形如
`trace_index 0 / message_index 16 / path /content`）+ `quote`；数据里没有“步骤序号”概念，
未与轨迹接口步骤对齐。

**9. `user_ids` / `trace_ids` 上限、更新延迟？**
上限沿用协议：`user_ids` 5000、`trace_ids` 1000（超过返回 413）。
分析结果按天写入 JSONL，服务每 30 分钟增量重建索引（`REFRESH_SECONDS`），
所以延迟 ≈ 文件落盘时间 + 最多 30 分钟；`meta.data_updated_at` 取最新文件的 mtime。

## 三、已知缺口（需要后续决策）

1. **意图编码是我们自己的映射**：`task`/`subtask` 是中文自由文本，`T01` / `T01.S02` 由
   `taxonomy/intent_2026-10.json` 固定。如果分析组另有正式编码体系，替换这个 JSON 即可，
   接口不用改。
2. **未聚类问题不计入错误**：影响约 20% 的 trace。要补，得让聚类流水线覆盖全部日期/模型，
   或在 `item_index` 缺条目时回退到 `problem.component_family` 的环节编码。
3. **不做跨版本映射**：聚类树升版后旧结果不会映射到新编码。
4. **`is_correct` 全为 `null`**：数据里这个字段没有填，详情里照实返回 `null`。
5. **问财 / lumi / forecast 不在本服务范围**：`dataset` 只有 `aime_eval`；
   其它产品要各自接一套，或者扩 `dataset` 枚举。

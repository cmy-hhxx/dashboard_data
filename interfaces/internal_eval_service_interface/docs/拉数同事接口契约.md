# 数据拉取同事接口契约（TraceCollectorAdapter）

本服务将“把测试问句交给数据拉取/推理系统、收集返回 trace”抽象为可插拔的 `TraceCollectorAdapter`，支持 **TaskManager 推理直连（`task_manager`，⚠️ 仅推理触发侧已通，标准 Litefusion 异步取数待接，见 §0）**、**共享目录投递（`file_drop`）** 与 **自定义 HTTP 异步派单（`http`）**（以及 `mock` 联调模式）。

---

## 0. TaskManager 推理接口对接现状与已知缺口（`INTERNAL_EVAL_COLLECTOR_MODE=task_manager`）

> **⚠️ 已知数据口径缺口（当前阻塞正式上线，待内部 Litefusion 异步链路走通后切换）**
>
> - TaskManager（`http://10.217.216.85:8888/api/v1/task`）实际只负责**触发推理并记录基础信息与会话索引**（每个 case 在各 step 上的 `session_id` / `trace_id`，见 `GET /tasks/{id}/cases`）。
> - TaskManager 返回的 `judge_data`（`GET /tasks/{id}/judge/{key}/download`）**不符合标准 `eval_harness` 评测输入口径**：它只是推理侧记录的摘要信息（`chain` / `text_answer` 等），**不包含完整的 Litefusion 数据**（完整 `llm_turn.input_messages`、系统/Skill 上下文、观测埋点等）；而 **Litefusion 数据是异步落盘/可查的**，与推理完成存在时间差。
> - 当前代码中的 `TaskManagerCollectorAdapter` 已跑通**触发与调度闭环**（建集 → 建任务 → 启动 → 轮询 → `retry-recall`/`fill_missing`/`reset_failed` 自动恢复 → 取消透传），但取数环节暂时拉取 `judge/download` 并做字段转换，**仅作链路联调验证，不可作为正式评测口径**。
> - **后续补齐方向**：待内部异步 Litefusion 拉数通道就绪后，将 `internal_eval/collectors.py` 中的 `judge/download` 步骤替换为「按 `GET /tasks/{id}/cases` 产出的 `(session_id, trace_id)` 异步等待并拉取标准 Litefusion trace，回填 `case_key` 后送入 `/ingest`」即可，上游派单与下游清洗/评测/聚类主流程不变。

当前 `TaskManagerCollectorAdapter` 已实现的 4 步（其中第 3 步待替换为异步 Litefusion 拉数）：

1. **分批建数据集（已通）**：按每批 ≤ 100 条调用 `POST /testsets` + `POST /testsets/{id}/append`，`case_id` 固定为 `<run_id>_<case_key>` 确保前后配对无歧义；
2. **双边合并建任务与启动（已通）**：将本次活跃 `sides`（如 `before` / `after`）组装为同一 TaskManager 任务的多个 `pipeline.steps[]`（支持复制 `template_task_id` 样板并叠加各侧 `is_pre`、`agent_id`、`mode`、`is_deep`、`ab_test_content`、`lumi_profile_id` 等覆盖），调用 `POST /tasks` 与 `POST /tasks/{id}/start`（带 `X-User-Id` 白名单鉴权头）；
3. **数据拉取（⚠️ 暂用 `judge/download` 占位，待替换为异步 Litefusion 拉取）**：当前后台轮询 `GET /tasks/{id}` 与 `GET /tasks/{id}/items` 后拉取 `GET /tasks/{id}/judge/{key}/download` 并转成简化版 Adapter `b` 结构送入 `/ingest`；正式接入时需改为按 `session_id` / `trace_id` 异步等待并获取标准 Litefusion 完整 trace；
4. **自动恢复与取消透传（已通）**：任务收敛时若有 `partial_count > 0` 或 `failed_count > 0`，自动按需依次执行 `POST /retry-recall`（日志未就绪类错误）→ `POST /fill_missing` / `POST /reset_failed` + `POST /start`（默认最多 2 轮）；若调用方取消本服务任务，自动调用 `POST /tasks/{id}/cancel`；状态持久化在 `98_service/dispatch/TASK_MANAGER_STATE.json`，支持服务重启后断点续轮询与 `/retry-failed` 复用原任务补跑。

## 1. 我方准备并下发的两份问句 JSONL

任务启动抽题后，我方会在该轮次的 `98_service/dispatch/` 下产出：
- `before_questions.jsonl`（发版前 Agent 待测问句）
- `after_questions.jsonl`（改版后 Agent 待测问句）
- `DISPATCH_MANIFEST.json`（含文件路径、目标回传目录、HTTP 回调路径清单）
- （可选配置 `INTERNAL_EVAL_DISPATCH_SPLIT=by_turn|both` 时，额外产出 `single_turn.jsonl` 与 `multi_turn.jsonl`）

每行 JSON 格式如下：

```json
{
  "run_id": "run_20261124_123000_a1b2c3",
  "version": "1124",
  "side": "after",
  "agent": {"name": "aime-v20261124-rc1"},
  "model": "aime_expert",
  "case_key": "eq_00001",
  "eq_index": 1,
  "case_id": "run_20261124_123000_a1b2c3_after_eq_00001",
  "source_trace_id": "20003020179399888704300000000276",
  "source_session_id": "thread_4fe164f3ea274a0983af85e8ffb3a1c5",
  "question": "How do I get them to do it all in one payment",
  "turn": "multi",
  "session_round": 11,
  "history_messages": [
    {"role": "user", "content": "..."},
    {"role": "assistant", "content": "..."}
  ]
}
```

> **配对铁律**：回传的每条 trace 请务必保留 `case_key`（如 `"eq_00001"`）或保留 `meta.case_id` 末尾的 `_eq_00001`，用于将 `before` 与 `after` 精准同题配对。

## 2. 回传方式 A：HTTP 流式回推（推荐，边拉边评边聚）

每跑完 1 条或一小批 trace，立即回调：

```bash
POST /api/v1/internal-eval/runs/<run_id>/ingest
Content-Type: application/json
```

```json
{
  "side": "after",
  "traces": [
    {
      "case_key": "eq_00001",
      "trace_id": "new_trace_id_001",
      "session_id": "new_session_id_001",
      "request_time": "2026-11-24T12:35:00Z",
      "meta": {
        "trace_id": "new_trace_id_001",
        "session_id": "new_session_id_001",
        "case_id": "run_20261124_123000_a1b2c3_after_eq_00001",
        "question": "How do I get them to do it all in one payment"
      },
      "messages": [
        {"role": "user", "type": "user_question", "content": "..."},
        {"role": "assistant", "type": "final_answer", "content": "..."}
      ]
    }
  ]
}
```

单题拉取失败或整边拉取结束时，回调：

```bash
POST /api/v1/internal-eval/runs/<run_id>/collector-events
Content-Type: application/json
```

```json
// 单题失败
{"side": "after", "event_type": "case_failed", "case_key": "eq_00042", "error_code": "AGENT_TIMEOUT", "error_message": "Agent 响应超时"}

// 整边完成（completed / partial / failed）
{"side": "after", "event_type": "completed", "total_sent": 999}
```

## 3. 回传方式 B：共享目录文件投递（无需 HTTP 回调）

在弗吉尼亚同盘 `/mnt/aime_eval_ssd` 上，拉数程序也可以直接持续追加写入：
- `<round_dir>/98_service/raw_traces/before/*.jsonl`
- `<round_dir>/98_service/raw_traces/after/*.jsonl`

服务后台 tailer 会以 2 秒粒度增量读取新写入的完整行并立刻送入清洗 → 评测 → 聚类；整边写完后在对应目录下创建一个空文件 `_DONE` 即可触发收尾。

## 4. 派单协议（`INTERNAL_EVAL_COLLECTOR_MODE=http`）

当拉数同事提供 HTTP 派单端点 `INTERNAL_EVAL_COLLECTOR_BASE_URL` 后，我方会在任务进入 `dispatching` 阶段时自动发起：

```http
POST {INTERNAL_EVAL_COLLECTOR_BASE_URL}/submit
Content-Type: application/json
```

请求体包含 `run_id`、`version`、`model`、`tier`、`sides`、`before_agent`、`after_agent`、`dispatch_files`（两份 JSONL 绝对路径）、`raw_trace_drop_dirs` 与我方 `ingest_path` / `events_path` 回调路径。后续同事接口字段如有调整，只需修改 `internal_eval/collectors.py` 中 `HttpCollectorAdapter` 一处，主流程零改动。
